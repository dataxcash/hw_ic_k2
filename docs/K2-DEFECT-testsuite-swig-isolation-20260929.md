**根因**：套件在**同一进程**内跑全部用例；其中若干用例会**改板**（`apply_routes` / `move_block` / `move_parts`）——
按 R964 的既有纪律「**改板必须在子进程**」，这些用例本应在子进程里跑；一旦**新增的用例**在同进程里触碰了改板路径，
SWIG 类型态即被破坏，**后续所有读板用例级联失败**（失败点与真正肇因**不在同一个用例**，故极难定位）。

**回退验证**：`git checkout` 回退本窗三处补墙的代码与测试 ⇒ **SELFTEST_EXIT=0 · 69/69 PASS**（证明肇因即本窗改动路径）。

## 二、为何这是**能力缺口**（非一次性）

- 现象：**套件无隔离** ⇒ 任何新增"会碰板"的回归件都可能**毒化整条套件**，而失败点离肇因很远；
- 后果：想给"框外坐标＝不可能输出"补**每道工序一个回归件**（#K2-380 §二 的硬要求）时，**补不进去**——这正是本窗卡住的地方；
- 归类：**测试基建缺口**（与 C25「声称≠工件」相邻但不同：这里是**判据可跑性**被基建限制）。

## 三、补法（下一窗，一次实现）

1. **回归件走子进程**：测试内的**一切改板调用**一律经 `tools/eda_eng.sh`（子进程）——本仓 `_cli` 助手已是此形，
   新回归件必须**只用** `_cli`，**禁止**在测试进程内直调 `apply_routes/move_block/move_parts`；
2. **一行式自检**：套件入口加**哨兵**——用例内若直调上述函数即**立即失败并具名**（防止后来者再毒化）；
3. 然后补 #K2-380 §二 的三处回归件（RIP 切点／缝合透传／落笔前检查）；
4. **改板守卫**（#K2-380 §二.3）实现时**不得**改变既有返回值语义（本窗实测：动 `apply_routes` 的返回/早退路径即触雷）——
   改为**新增**可选参数、**默认不改行为**，并在**子进程**用例里验证。
